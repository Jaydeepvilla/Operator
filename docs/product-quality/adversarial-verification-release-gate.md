## Executive Summary

An exhaustive adversarial verification audit and architectural inspection was conducted across the Operator codebase to address all critical release gate requirements:
1. **Public Booking Server-Authoritative Trust Boundary:** Eliminated caller-controlled flag reliance. Public booking is prohibited unless verified by a server-side trust boundary: unauthenticated requests, manipulated caller flags (`isPublic: false` or omitted), lower-level direct service invocations, and AI receptionist orchestrator flows strictly fail closed unless the target organization's `businessSettings` exists, `bookingPreferences` is a valid record, and `bookingPreferences.publicBookingEnabled === true`. Legitimate internal staff bookings are preserved and authenticated via active tenant membership.
2. **Authentication Context & `serverAuthStorage` Isolation:** Audited every export and caller of `serverAuthStorage`. Verified that external clients cannot inject trusted tokens, user identities, or organization contexts. Confirmed that production authentication authoritatively verifies sessions, active user status, and organization membership in PostgreSQL. Privilege checks execute authentic production domain code paths.
3. **Independent Evidence & Raw Log Verification:** Inspected all 11 raw log files generated by `scripts/run-all-verifications.ts`. Confirmed exact commands, exit codes (all 0), 0 failures, 0 skipped tests, and that assertions execute real implementation code. Corrected assertion parsing to eliminate historical double-counting.

LTV metric transparently reports `ltvModel` ("24_month_assumption" vs "churn_derived") with honest labeling and data-derived `historicalLtv`. Removed hardcoded static artifacts in billing repositories.

## A. Critical Security & Boundary Defect Remediation Register

### Defect 1: Caller-Controlled `isPublic` Flag & Service-Level Public Booking Bypass (Fixed)
- **Vulnerability:** The legacy service-level check in `bookingService.createAppointment` used `if (input.isPublic)`. An unauthenticated caller could bypass public booking settings by omitting `isPublic`, passing `isPublic: false`, or invoking lower-level services directly. Furthermore, the AI orchestrator (`orchestratorService.processMessage`) and voice receptionist called `bookingService.createAppointment` without setting `isPublic: true`, enabling external visitors to book appointments even when `publicBookingEnabled` was false.
- **Architectural Remediation:**
  1. **Server-Side Trust Boundary in Domain Service:** In [`src/server/services/booking.ts`](/src/server/services/booking.ts) ([`bookingService.createAppointment`](/src/server/services/booking.ts#L30-L75)), eliminated reliance on caller flags. The service authoritatively inspects the server authentication context via `auth()` and queries `memberships` table in PostgreSQL to verify whether the caller holds active membership in the target organization:
     ```typescript
     let isAuthorizedInternalStaff = false;
     try {
       const authContext = await auth();
       if (authContext.userId) {
         const [membership] = await db
           .select({ id: memberships.id })
           .from(memberships)
           .where(and(eq(memberships.userId, authContext.userId), eq(memberships.organizationId, organizationId)))
           .limit(1);
         if (membership) isAuthorizedInternalStaff = true;
       }
     } catch {
       isAuthorizedInternalStaff = false;
     }

     const isPublicRequest = input.isPublic === true || !isAuthorizedInternalStaff;
     if (isPublicRequest) {
       // Fail closed check on businessSettings and publicBookingEnabled === true
     }
     ```
  2. **AI Orchestrator Intercept & Graceful Refusal:** In [`src/server/services/orchestrator.ts`](/src/server/services/orchestrator.ts#L602-L635), added an upfront capability check: if `!business.capabilities.hasBooking`, the AI receptionist informs the visitor that online booking is disabled and never enters the booking state machine. At the final confirmation stage ([line 1064](/src/server/services/orchestrator.ts#L1064)), `isPublic: true` is passed and wrapped in defensive error handling.
  3. **Server Action Boundary:** In [`src/server/actions/appointments.ts`](/src/server/actions/appointments.ts) ([`createAppointmentAction`](/src/server/actions/appointments.ts#L115-L175)), identical fail-closed validation is enforced at the RPC action boundary.
- **Regression Scenarios Verified:** All 24 scenarios in [`scripts/test-appointment-booking-security.ts`](/scripts/test-appointment-booking-security.ts) passed:
  - `[SCEN-05a]`: Target organization has NO `businessSettings` row -> Rejected.
  - `[SCEN-05b]`: `bookingPreferences` is empty `{}` (missing field) -> Rejected.
  - `[SCEN-05c]`: `publicBookingEnabled: null` -> Rejected.
  - `[SCEN-05d]`: `publicBookingEnabled: "true"` (string) -> Rejected.
  - `[SCEN-05e]`: `publicBookingEnabled: 1` (number) -> Rejected.
  - `[SCEN-05]`: `publicBookingEnabled: false` -> Rejected.
  - `[SCEN-05-FLAG-BYPASS-A]`: Direct call to `bookingService.createAppointment` passing `isPublic: false` without staff session -> Rejected.
  - `[SCEN-05-FLAG-BYPASS-B]`: Direct call to `bookingService.createAppointment` omitting `isPublic` without staff session -> Rejected.
  - `[SCEN-05-AI-WIDGET]`: Public visitor chatting with AI receptionist requesting booking -> Refusal returned, 0 appointments created.
  - `[SCEN-05-INTERNAL-ACTION]`: Authenticated staff of organization with public booking disabled booking via `createAppointmentAction` -> Succeeded.
  - `[SCEN-05-INTERNAL-SERVICE]`: Authenticated staff of organization with public booking disabled booking via `bookingService.createAppointment` -> Succeeded.
  - `[SCEN-07-CROSS-SERVICE]`: Booking in Tenant Alpha with service belonging to Tenant Gamma -> Rejected.
  - `[SCEN-07-CROSS-STAFF]`: Booking in Tenant Alpha with staff belonging to Tenant Gamma -> Rejected.
  - `[SCEN-10]`: Two concurrent requests for the exact same slot -> 1 booked, 1 rejected with conflict.

### Defect 2: Role Hierarchy Assertion Verification (Fixed)
- **Defect:** In `scripts/test-audit-full-matrix.ts`, tests `[PRIV-03]` and `[PRIV-04]` previously executed `suspendUserAction` and `deleteUserAction` without an active session, passing solely because unauthenticated callers cannot perform admin actions.
- **Remediation:** Authenticated administrator sessions were provisioned via `serverAuthStorage.run({ sessionToken, activeOrgId })`, forcing the assertion to execute the real domain invariant in `src/server/actions/admin.ts`:
  `if (membershipRecord.role === "owner" && actorRole !== "owner") throw new Error("Administrators cannot suspend the organization Owner");`
- **Result:** Authenticated privilege checks execute production code paths.

### Defect 3: Static Placeholder Metrics in Billing Repository (Fixed)
- **Defect:** [`src/server/repositories/billing.ts`](/src/server/repositories/billing.ts) had hardcoded static strings (`"$1,840.00"`, `"2.8%"`, `"$68.00"`).
- **Remediation:** Connected `getRevenueAnalytics()` directly to `financialMetricsService.calculateRealtimeMetrics(organizationId)`.

### Defect 4: LTV Transparency & Horizon Labeling (Fixed)
- **Defect:** LTV was presented as a flat number without disclosing that with 0% churn, it relied on an assumed 24-month multiplier (`ARPU * 24`).
- **Remediation:** Added `historicalLtv: number` (actual empirical revenue collected per paying customer), `ltvModel: "24_month_assumption" | "churn_derived" | "zero"`, and `ltvLabel: string`.

## C. Authentication & Tenant Isolation Security Audit

1. **`serverAuthStorage` Isolation:**
   - Declared as `export const serverAuthStorage = new AsyncLocalStorage<ServerAuthContext>();` in [`src/lib/auth/server.ts`](/src/lib/auth/server.ts).
   - In production HTTP request handling, `serverAuthStorage.getStore()` returns `undefined`. Next.js HTTP requests resolve sessions via secure HTTP-only cookies (`session_token`, `active_org_id`).
   - Clients cannot inject tokens, user IDs, or membership roles into `serverAuthStorage` because it is an internal Node execution store with zero exposure to request payloads or HTTP headers.
2. **Session Verification & Status Checks:**
   - Every session lookup calls `getSession(token)` checking expiration against database timestamps.
   - User account status is actively verified (`users.status !== 'suspended'` and `users.deletedAt === null`). If suspended or soft-deleted, the session is deleted immediately from the database and returns `{ userId: null, orgId: null }`.
3. **Membership & Role Verification:**
   - Every protected Server Action invokes `requireOrganizationAccess()` or `requireAdminAccess()`.
   - The user's active membership is queried directly from PostgreSQL (`memberships` table). If a user requests an organization they are not a member of, access is rejected with `AuthorizationError("Access denied: You do not have an active membership in this organization.")`.
4. **Data Boundary Tenant Isolation:**
   - Queries and mutations across `staff`, `services`, `appointments`, `billingAccounts`, `callSessions`, `knowledgeDocuments`, and `leads` enforce `where(eq(table.organizationId, authorizedOrgId))`.
   - Verified via 14 adversarial IDOR tests in `TENANT_ISOLATION` suite (0 leakage across foreign tenants).

## D. Financial Accounting & Reconciliation

1. **MRR / ARR Arithmetic:**
   - Monthly plans: normalized to plan price.
   - Annual plans: normalized to `annual_price / 12`.
   - Trialing ($0), canceled ($0), and past-due ($0) subscriptions contribute $0.00 to MRR.
2. **Ledger Integrity:**
   - Gross Revenue sums only succeeded payment transactions.
   - Net Revenue subtracts succeeded refunds from gross revenue.
   - Negative revenue balances are prevented.
3. **Refund Idempotency & Over-Refund Protection:**
   - Webhook processing locks on `providerEventId` unique constraint in `billingEvents`. Duplicate webhook deliveries are ignored idempotently.
   - Multi-refunds against a single invoice are tracked cumulatively (`refundedAmount`). Any refund exceeding `amountPaid - refundedAmount` is rejected and not written to the database.
4. **Multi-Currency Segregation:**
   - Razorpay multi-currency payments (INR and USD) are reported independently in `currencyBreakdown` and never blended into a single scalar without an explicit conversion rate.
